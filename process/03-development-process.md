These are founder directives, not suggestions.### Work in small, reviewable incrementsPrefer clear tasks with explicit acceptance criteria tied to Shortcut stories. Onewell-defined task beats several speculative ones. This was the standing executionpolicy: **WIP = 1**.### No invented requirements or architectureDerive from Shortcut or agreed docs. Mark unknowns as unknown. If a requirement ismissing, ask; do not fill the gap with a plausible guess and ship it.### Verification before claiming doneA change is "done" only when its acceptance criteria are verified ΓÇö tests pass andbehavior is confirmed. Code that compiles is not done. A demo on localhost is notdone. A PR that "should work" is not done.### Commit hygiene- **Incremental commits if and only if the build is passing.** Never commit on a  red build. Fix or isolate first.- **Run the formatter before committing** if the project has one configured (run it  in the containerized toolchain).- **Prefix every incremental commit with `[<STORY>]`**, e.g. `[SC-131]`. The story  is the Shortcut story the work belongs to.- **Message standards:** max 50 characters excluding the prefix, capitalize the  first word, no trailing period, imperative mood. Example:  `[SC-131] Add JWT verification filter`.- Keep commits focused and logically separated.### PR-based review flow- **Every** feature or fix goes branch ΓåÆ push ΓåÆ **open a GitHub PR** ΓåÆ merge to  `main` only after review. Direct pushes or merges to `main` from feature branches  without a PR are not allowed.- **CI/build status must be green on the PR head** before merging.- **No merge without an approving review recorded on the PR.**- Security-sensitive work (auth, trust, integrations) additionally requires  **Omar's explicit approval**.### PR and comment attributionThis is unusual and important. Read it carefully.**Established.** Commits intentionally attribute to the shared GitHub account(**Arham4**). Do **not** change that. Keep the PR title convention(`[SC-###] ...`, no agent prefix). Instead, the acting specialist must beidentified **inside the PR**:- State the acting agent's profile name in the **PR body** (e.g. an `Author: hamza`  line or `<!-- attribution: hamza -->` marker).- Open each **comment or review comment** with `[hamza] ...`.- If a human wrote it, use the human's name.This exists because git author and PR titles are shared, so attribution had to livesomewhere auditable. It works, but it is easy to forget. If you drop theconvention, PR authorship becomes unattributable.### The shared-account approval workaround**Established.** Because the reviewer and author are the same GitHub account(Arham4), GitHub blocks a formal `APPROVED` review on your own PR. The team'sworkaround, encoded in the coordination gate prompt:> An open PR **is** merge-approved when **both** attributed reviewer comments> (one starting `[omar]`, one starting `[yusuf]`) state **"Verdict: APPROVE"** ΓÇö> treat those as the valid approving reviews even if `reviewDecision` is empty or> `COMMENTED`. One reviewer's approval alone is not enough.Still required: the PR must be **MERGEABLE** (no conflict), the build must begreen on the head, and the owner must have approved after the specialist roundsconverged. If a PR is conflicting, rebase or merge `main` in; do not blocksilently.If you move to a proper multi-account setup, this workaround can be deleted. Untilthen, it is the only way to satisfy "no merge without approval" on a single account.### Security review division of labor**Established** (founder-ratified):- **Omar ΓÇö Security Reviewer (static, code-level).** Reviews diffs and PRs for  vulnerability classes; approves or blocks PRs on security grounds; defines  security requirements, threat models, and attack cases. Does **not** run exploit  scripts or own test tooling.- **Yusuf ΓÇö QA / Adversarial Testing (dynamic, runtime).** Verifies acceptance  criteria against real behavior; owns the "break it" pass (running the app in  containers, executing Omar's attack cases); owns QA conventions and regression  checks. Reports findings; does **not** adjudicate security risk ΓÇö Omar does.- **Handshake:** Omar defines what to attack and why ΓåÆ Yusuf executes and reports ΓåÆ  Omar adjudicates (real risk vs. accepted).This split is genuinely good and worth preserving. It prevents the common failurewhere the person who wrote the code also declares it secure.### Honesty in status reporting (amanah)Report real results. Surface blockers and unknowns rather than papering over them.Do not claim success without verifying it. This was stated as a religious andprofessional obligation, and it is the rule most worth carrying forward.## How the execution loop actually worked**Established** from the cron job definitions and `hff_check.sh`.There were four scheduled jobs:| Job | Schedule | Role ||-----|----------|------|| HFF coordination gate | Every 30 min, 00:00 and 09:00ΓÇô23:00 | Merge review, dispatch, unblock || HFF sprint plan + execute | Daily 09:00 and 17:00 | Sprint lifecycle, planning, opening/closing || HFF coordination gate (overnight) | 03:00 and 06:00 | Same as gate, quiet hours || HFF deploy watchdog | Every 15 min | Self-heal the preview stack |### The action-gated designThe gate is deliberately **deterministic and cheap**. `hff_check.sh` prints afingerprint containing:- `action=0|1` ΓÇö whether a coordination action is needed- `prs=<sorted open PR numbers>` ΓÇö so the fingerprint changes when a PR opens,  merges, or closes- `reviews=<per-PR reviewDecision:states:last-review-timestamp>` ΓÇö so the  fingerprint changes when a review lands on an **already-open** PRThe Hermes cron `monitor` gate compares the output to the previous tick and wakesthe LLM **only when the fingerprint changes**. This prevents the agent from wakingevery 30 minutes to say "nothing to do."The action logic, in priority order:1. If any PR is open ΓåÆ `action=1` (merge review).2. Else if ready cards exist and no worker is running ΓåÆ `action=1` (dispatch).3. Else if blocked cards exist ΓåÆ `action=1` (unblock).4. Else `action=0`.Two bugs were fixed during development and are documented in the script's comments;both are worth knowing because they illustrate the failure mode:- **Count-vs-list bug:** emitting only a count meant a *new* PR arriving while  another was already open did not change the hash, so the gate never woke. Fixed  by emitting the sorted PR list.- **Review-on-open-PR bug:** the PR list does not change when a review lands on an  already-open PR, so the gate never re-evaluated. Fixed by emitting per-PR review  state and timestamps.### The agent's job in a tickThe gate prompt told the agent to:1. Read the injected diff; if it is only cosmetic, treat as nothing to do.2. Run `hermes kanban list`.3. **merge_review:** verify and merge open PRs (with the approval workaround above).4. **dispatch:** dispatch the next ready card (`hermes kanban dispatch`), WIP=1.5. **unblock:** clear resolved blockers.6. If nothing was done or nothing new, respond with **exactly** `[SILENT]`.7. Only report if something actually happened (merged/dispatched/unblocked/synced).The `[SILENT]` convention is important: it kept the Discord channel quiet so that amessage meant something. If you keep any automation, keep that property.### The sprint jobThe daily 09:00/17:00 job owned the sprint lifecycle end-to-end with full autonomy:- Diagnose sprint state **from work, not the calendar**. An iteration end date alone  is not evidence the sprint is alive.- A sprint is **exhausted** when no card is running and no ready/todo card is  actually executable (founder-gated cards do not count).- A sprint is **healthy** when there is running work or executable ready cards.- If healthy: do nothing, report honestly, stop.- If exhausted or absent: close the old iteration, create a new one named  `M1 Sprint N ΓÇö <Theme>` with a real ~7-day window, and plan a coherent milestone  across backend, frontend, edge cases, and review gates.- Source scope **only** from real Shortcut stories in backlog epics that are not  done. Never invent features. Own-initiated tickets are bug fixes only.- Reconcile against the repo before queueing: inspect what is already built so you  do not re-card done work. Verify the foundation is green before dispatching on  top of it.- Every story goes in its epic **and** its iteration (founder rule).### Iteration budget behaviour**Observed.** Kanban tasks carry a max-iteration budget. When it is exhausted thecard is blocked with a message like *"Iteration budget exhausted (40/40) ΓÇö taskcould not complete within the allowed iterations."* This is a worker-resourcefailure, not a product blocker. The blocked card `t_63bc37f1` failed this way.If you see this, the fix is to increase the budget or split the card ΓÇö not toinvestigate the product.## What to keep and what to dropYou are moving to a synchronous model. My recommendation, stated as arecommendation and not a requirement:**Keep:**- Shortcut as product truth; the repo as implementation truth. The split is sound.- TDD for backend. It is the reason the backend is in good shape.- PR-based review with green build and a recorded approval. This caught real issues.- The attribution convention while the GitHub account is shared. Cheap and useful.- The security/QA split between static review and dynamic break-it testing.- The honesty rule. It is the cheapest quality mechanism you have.**Drop or simplify:**- The seven-persona structure, unless the founder explicitly wants to keep it. It  produced good work but the coordination overhead is what made the project hard to  follow. A single agent with clear domain checkpoints would be easier to manage.- The 30-minute action gate. In a synchronous model you will know what is happening;  a 30-minute autonomous loop is more machinery than you need. Keep the deploy  watchdog only if you fix its liveness check (see [05](05-operations-and-infrastructure.md)).- The 42 historical worktrees under `.worktrees/`. They are noise now. Prune them  after confirming nothing unmerged is needed.- The `[SILENT]` convention only if you no longer use Discord as the status channel.  If you do, keep it ΓÇö a silent channel is a feature.
