## Findings

### F1 (blocking) — `distinct` can never insert

A held duplicate only arises from `findByNormalizedLocation`, which matches rows
with `provenance IS NOT NULL`. V22's `uq_restaurant_listings_research_location`
is unique on the same 6-dp `(location_lat_6, location_lng_6)` over exactly that
predicate. So every held-duplicate candidate is already inside the index that
forbids the `distinct` insert:

```
ERROR: duplicate key value violates unique constraint
"uq_restaurant_listings_research_location"
Detail: Key (location_lat_6, location_lng_6)=(44.800000, -79.800000) already exists.
```

Fail-closed (whole batch rolls back) but the documented food-court decision is
unusable. Needs a product/schema decision: carve out an explicit `distinct`
decision from the V22 backstop, or remove `distinct` from
`docs/features/SC-211/09-decisions-and-metros.md`.

### F2 (medium, fail-closed) — a merge does not redirect a concurrent write

When one batch both writes to listing A and decides `same-venue` A→B, preview
emits `Update(A)` plus `merge A→B`. Apply merges first (A deleted), then the
write fails: `IllegalStateException: listing ... vanished between preview and
apply`. Nothing is committed, but the batch cannot load and the diff does not
warn. Fix: rewrite every write whose target is a `retireId` to the keeper (as
`plan()` already does inside one candidate) before deduping writes.
