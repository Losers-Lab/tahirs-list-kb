## Non-blocking observations

1. **A redirected write can carry the retired row's identity onto the keeper.**
   `redirectWrites → dedupeWrites → mergeWith` keeps the strongest-evidence
   candidate, which may be the redirected one, and `updateImported` rewrites
   `venue_key`/name/address/location. Observed: keeper key `e1…e1` became
   `e9…e9`, name "Gamma Row", location (13.4, 35.4); `findByVenueKey(e1…e1)` is
   now null, so a later row carrying the old key can no longer match by key and
   can insert the duplicate the merge was meant to prevent.
2. **Report double accounting:** a no-coordinate row that geocodes to nothing is
   rejected `NO_GEOCODER_MATCH` **and** counted in gaps as outside every metro.
3. **Report hole:** a row inside a configured but unselected metro is counted
   nowhere (`fetched=0`, no reject, no gap).
4. A contradictory same-venue pair (A→B and B→A) fails closed with
   `BatchPlanException: merge keeper … does not exist`; nothing committed, but
   the preview shows no warning.
